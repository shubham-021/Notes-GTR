## Defining Traits

Rust lets you abstract over types with traits. They're similar to interfaces:

```rust
trait Pet {
    fn talk(&self) -> String;

    fn greet(&self) {
        println!("Oh you're a cutie! What's your name? {}", self.talk());
    }
}
```

## Implementing Traits

To implement a trait for a type, you use an `impl Trait for Type { .. }` block:

```rust
struct Dog {
    name: String,
    age: i8,
}

impl Pet for Dog {
    fn talk(&self) -> String {
        format!("Woof, my name is {}!", self.name)
    }
}

let fido = Dog { name: String::from("Fido"), age: 5 };
dbg!(fido.talk());
fido.greet();
```

Just having matching methods is not enough: a `Cat` type with a `talk()` method would not automatically satisfy `Pet` unless it is in an `impl Pet` block.

If a trait method has no body, the implementing type must provide it. If a trait method has a body (like `greet` above), the implementing type gets it automatically but can override it.

## Multiple Trait Implementations

You can implement multiple traits for the same type:

```rust
trait Pet {
    fn talk(&self);
}

trait Animal {
    fn eat(&self);
}

impl Pet for Dog {
    fn talk(&self) {
        println!("Woof!");
    }
}

impl Animal for Dog {
    fn eat(&self) {
        println!("Dog is eating");
    }
}
```

So `Dog` has its own methods, plus `Pet` behavior, plus `Animal` behavior. These `impl` blocks can even be placed in different modules or files:

```
dog.rs
    struct Dog
    impl Dog { ... }

pet.rs
    impl Pet for Dog { ... }

animal.rs
    impl Animal for Dog { ... }
```

As long as Rust's rules about visibility and trait implementations are satisfied.

## Supertraits

```rust
trait Animal {
    fn leg_count(&self) -> u32;
}

trait Pet: Animal {
    fn name(&self) -> String;
}
```

`trait Pet: Animal` means "anything that is a `Pet` must also be an `Animal`." This creates a requirement:

```
Pet → (requires) → Animal
```

So if you write `impl Pet for Dog`, Rust will also require `impl Animal for Dog`:

```rust
struct Dog(String);

impl Animal for Dog {
    fn leg_count(&self) -> u32 {
        4
    }
}

impl Pet for Dog {
    fn name(&self) -> String {
        self.0.clone()
    }
}

let puppy = Dog(String::from("Rex"));
println!("{} has {} legs", puppy.name(), puppy.leg_count());
```

This is useful because `Pet` can now assume that the type has all the behavior of `Animal`. For example, a default method inside `Pet` could call `self.leg_count()` even though `leg_count()` is not defined inside `Pet`:

```rust
trait Pet: Animal {
    fn name(&self) -> String;

    fn introduce(&self) {
        println!(
            "I'm {}, and I have {} legs",
            self.name(),
            self.leg_count()
        );
    }
}
```

This is sometimes called "trait inheritance" but it should not be expected to behave like OO inheritance. It just specifies an additional requirement on implementations of a trait.

## Associated Types

Associated types (sometimes called "output types") let a trait declare a placeholder type that implementations must specify.

```rust
#[derive(Debug)]
struct Meters(i32);

#[derive(Debug)]
struct MetersSquared(i32);

trait Multiply {
    type Output;
    fn multiply(&self, other: &Self) -> Self::Output;
}
```

`type Output` means: every type that implements `Multiply` must tell the trait what type the multiplication produces.

Inside the trait:

- `self` = the current instance/value
- `Self` = the type being implemented
- `Self::Output` = the `Output` type associated with the current type

The `::` is being used to access something associated with a type.

```rust
impl Multiply for Meters {
    type Output = MetersSquared;

    fn multiply(&self, other: &Self) -> Self::Output {
        MetersSquared(self.0 * other.0)
    }
}

println!("{:?}", Meters(10).multiply(&Meters(20)));
```

Here we're saying: for `Meters`, `Multiply` produces `MetersSquared`. So inside this implementation, `Self = Meters` and `Self::Output = MetersSquared`.

### Why Not Just Use a Generic?

You could imagine:

```rust
trait Multiply<T> {
    fn multiply(&self, other: &Self) -> T;
}
```

But associated types are useful when there should be one specific output type for a particular implementation. With the associated type version, Rust knows that `Meters`'s `Multiply` implementation always produces `MetersSquared`. There's exactly one answer, not a choice.

Mentally:

```
trait Multiply
    |- type Output = "you tell me the result type"

Meters implements Multiply
    |- Output = MetersSquared
```

## Deriving Traits

Supported traits can be automatically implemented for your custom types:

```rust
#[derive(Debug, Clone, Default)]
struct Player {
    name: String,
    strength: u8,
    hit_points: u8,
}

let p1 = Player::default();
let mut p2 = p1.clone();
p2.name = String::from("EldurScrollz");
println!("{p1:?} vs. {p2:?}");
```

- `Default` trait adds a `default()` constructor that initializes all fields to their default values (empty string, 0, etc.)
- `Clone` trait adds a `clone()` method for explicit deep copying
- `Debug` trait adds support for printing with `{:?}`

Derivation is usually provided for traits that have a common boilerplate implementation that is correct for most cases. For example, a manual `Clone` impl would look like this:

```rust
impl Clone for Player {
    fn clone(&self) -> Self {
        Player {
            name: self.name.clone(),
            strength: self.strength.clone(),
            hit_points: self.hit_points.clone(),
        }
    }
}
```

Not all of the `.clone()` calls above are necessary in this case (primitive types implement `Copy`), but this demonstrates the repetitive pattern that manual implementations would follow, which should help make the usefulness of `derive` clear.
